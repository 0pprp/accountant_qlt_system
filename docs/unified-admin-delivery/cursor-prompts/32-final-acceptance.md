### المقصود بالنقل
النظام الجديد لوحة واحدة وAPI مركزي وقاعدة PostgreSQL بمعمارية المشروع. القديم دليل للبيانات والأزرار والحسابات والانتقالات فقط؛ لا تستخدم API القديم في التشغيل، ولا gateway أو قواعد فروع أو مفاتيح مدينة قديمة. لا تقسّم الواجهة إلى لوحات حسب أسماء الأدوار. الدور قالب صلاحيات افتراضي، والحساب يحصل على الموروث مع Allow/Deny. حافظ على الوظيفة وغيّر التنظيم التقني والشكل فقط.

ابدأ بجدول لكل شاشة: الحقل/الزر → مصدره القديم (ملف + symbol) → القاعدة → بيانات الجديد → الصلاحية → الأثر → اختبار القبول. اقرأ الشاشة وكومبوزبل الاستدعاء ثم Controller/Service/SQL عند الحاجة. `docs/Qalaa_ALL_APIs_Inventory.xlsx` و`docs/REPO_FOLDERS_SHEET_AR_EN.md` فهارس اكتشاف؛ أوصاف وWhere used في Excel تقريبية وليست إثباتًا. راجع أيضًا تقرير parity الحالي. لا تفسر عنوان الزر على أنه يثبت وجود mutation. إذا كانت قاعدة مالية أو هوية كيان غير قابلة للحسم من المصدر، توقف عند تلك الجزئية وحدها وسجل سؤالًا محددًا، وأكمل المستقل عنها.

### التفويض ونطاق البيانات
- تبويب جاهز بدون صلاحية يظهر بقفل ويصل إلى AccessDenied بلا تركيب الصفحة أو طلب بياناتها؛ غير المنفذ لا يُقدّم كأنه مجرد قفل صلاحية.
- صلاحية دخول التبويب والقراءة مستقلة عن التعديل والإجراءات. امتلاك Update وحده لا يمنح Read ضمنيًا. سجل dependency في محرر الصلاحيات دون توسيع صلاحيات خفي. الأب يُفتح إذا أمكن دخول أحد الأبناء؛ لا تضف صلاحية أب تجبر المستخدم على شراء حقين لنفس القراءة.
- استخدم evaluator الحالي وRolePermissions/UserPermissions/UserPermissionDenials، لا نظام صلاحيات موازٍ ولا `if role == Director` داخل الشاشات أو الخدمات. الاستثناءات الأمنية لحساب Admin الحالي تُحفظ.
- API يتحقق من الصلاحية، الفروع المسموحة، المورد وملكيته/تكليفه الحالي. `branchId` مرشح لا إثبات تفويض. غيابه يعني جميع الفروع المسموحة فقط عندما يدعم العقد التجميع. تحقّق من customer/order/list/follower/employee ID المستهدف ومنع IDOR وmass assignment.
- افصل الحقول المالية والمستندات والمواقع والتصدير عند اختلاف صلاحياتها؛ لا ترسل الحقل المحظور للعميل أصلًا، ولا تعرضه صفرًا. إجمالي وتصدير وعدّادات الاستعلام تستخدم النطاق نفسه.
- احفظ نظام refresh وإبطال الجلسات الحالي. عند تغيير الفرع/الحساب/الصلاحيات، ألغ الطلبات القديمة وامنع تطبيق الرد المتأخر. Query keys تشمل الجلسة/النطاق والفلاتر والصفحة، وenabled يشترط جاهزية التفويض.

### تنظيم التنفيذ والعقود
أسماء المسارات والصلاحيات في هذا البرومبت **مقترحة للجديد**؛ افحص الموجودة أولًا، وأعد استخدام المقابل الصحيح مع توثيق الاسم النهائي، ولا تكسر مستهلكًا حاليًا.
Vue داخل `panel-admin-main/panel-admin-main/src/modules/{Feature}/`: `domain/types.ts`, `domain/queryKeys.ts`, `requests/queries`, `requests/mutations`, `composables`, `components`, `views`, `router.ts`. استخدم axios وVue Query وPrimeVue الموجودين. Management تنسيق وتنقل فقط؛ لا تحشر منطق المجالات داخله. سجّل الوحدة في registerModules حسب النمط الحالي.
Backend داخل `api-main/api-main/src`: Domain للقواعد والكيانات الجديدة اللازمة فقط؛ Application/{Feature}/Queries/Admin/{Operation} وCommands/Admin/{Operation} مع Handler/Validator/Response وResult Pattern؛ Infrastructure لـEF والملفات؛ Api/Controllers/V1/AdminArea لعقود HTTP. اتبع المسارات الفعلية وAGENTS، لا تنشئ repository عامة أو microservice دون حاجة.
اكتب DTOs محددة: required/nullable، enums، الوحدات النقدية، timezone، فلاتر allowlist، حد pageSize وترتيب ثابت مع ID tie-breaker. استخدم نمط الاستجابة والأخطاء الحالي. query scoped بـAsNoTracking وprojection وتجميع في DB، لا N+1 ولا تحميل جميع الصفوف قبل pagination. أضف indexes وفق الاستعلام وخطة تنفيذه لا بالتخمين.
لكل تعديل متعارض استعمل concurrency version المناسب للعقد الحالي و409. في القرار المالي: معاملة ذرية، audit before/after، ومنع تكرار الأثر بمفتاح عملية مناسب. لا تعالج double-click فقط بالواجهة. لا تستبدل دفعة حقيقية بـSalesRequest أو تسجلها مرتين. استعمل الأموال decimal، وحساب فترات بغداد الصحيح وحدود البداية والنهاية المتفق عليها.
إن احتاجت الميزة مخططًا جديدًا، المستخدم وافق على migration رسمي مع مراجعة وتجربة قاعدة معزولة؛ حافظ على snapshot واختبر apply على نسخة مماثلة. لا تجاهل PendingModelChanges ولا تطبق على الإنتاج ضمن هذا البرومبت. لا تنسخ بيانات أو أسرار الإنتاج محليًا.

## خطوات العمل والتصميم الخاص

اجمع CoverageMatrix لكل تبويب/زر/حقل مصدر، لا تقريرًا إجماليًا يقول كل شيء مكتمل. اختبر Admin ومدير ومراقب ومدير مبيعات وحسابًا مخصصًا يأخذ تبويبًا واحدًا من كل قسم. الدور الافتراضي لا يمنع تخصيص الحساب. اختبر Allow/Deny/Inherit وRead-only وwrite-without-read وتبديل الفرع والجلسة والروابط المباشرة والتصدير والمرفقات.
دورات فعلية مع التطبيقات: طلب بيع، تحديث حالة، عمل متابع، جباية مسموحة/ممنوعة، موقع، تكليف لجنة، إعلان وفيديو بحسب المنفذ. افصل Unit/Relational/API live/Browser/Application-device. اختبار API لا يساوي Flutter UI، وWeb لا يساوي Android.
اختبر burst أحداث Hub وإعادة الاتصال ومنع الأحداث بعد سحب الصلاحية، لا بيانات stale أو fetch storm. قس p50/p95 وحجم payload وعدد الاستعلامات على بيانات معزولة ممثلة ووثق حجمها وظروف القياس؛ لا تعد بزمن ثابت بلا دليل. خطط pagination والفهارس للقراءات الكبيرة.
راجع migration/model snapshot ونسخة clone وbackup restore؛ أخرج ReleasePlan يتضمن الإصدارات وترتيب المخطط/API/الواجهة وتوافق التطبيقات وrollback وحالة البيانات عند الرجوع. لا نشر ضمن هذه الحزمة؛ سلّم إصدارًا قابلًا للمراجعة والتفعيل. إن تعذر جزء اعرضه صراحة ولا تستبدله بصورة أو mock.
