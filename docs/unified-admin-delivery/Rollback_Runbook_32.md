# Rollback Runbook 32

**ميّز دائمًا:** رجوع **صورة التطبيق** ≠ رجوع **مخطط قاعدة البيانات**.

## أ) رجوع صورة API / Panel / Apps (دون لمس DB)

1. أوقف الخدمة الجديدة.
2. أعد نشر artifact الإصدار السابق (احتفظ ببصماته).
3. لا تستبدل مجلد التخزين/uploads.
4. أعد توجيه اللوحة إلى `dist` السابق.
5. Remint/أعد نشر التطبيقات السابقة عبر المتجر/التوزيع الجانبي.
6. Smoke: login + قراءة قوائم أساسية.

**قيود:** إذا كانت DB قد ترقّت إلى Branch31+ فقد تفشل الصورة القديمة على أعمدة/جداول جديدة أو تتجاهل سلوكًا مطلوبًا. لا تفترض التوافق.

## ب) رجوع مخطط قاعدة البيانات

1. **مفضّل:** استعادة **backup** أُخذ قبل migrate على بيئة معزولة ثم قطع التحويل.
2. لا تعتمد على `migrate down` غير مختبر كمسار إنتاج.
3. إن وُجدت بيانات جديدة بعد الترقية (تنازلات مطبّقة، زيارات، WrongSale): وثّق الخسارة قبل الاستعادة.
4. بعد الاستعادة: شغّل صورة API المتوافقة مع ذلك المخطط فقط.

## ج) رجوع جزئي لوحدة

| وحدة | إجراء |
|---|---|
| Waiver مالي بعد Apply خاطئ | لا «عكس تلقائي» في العقد الحالي — تصحيح محاسبي يدوي موثّق + قرار إداري؛ لا إعادة Apply للخصم |
| Feature flag / صلاحية | اسحب الصلاحية من الأدوار؛ الجلسات المفتوحة تُرفض على السيرفر عند سحب الحق |
| تطبيق مندوب | أعد تثبيت APK السابق؛ لا يصلح DB |

## د) متى تتوقف وترفع التصعيد

- فشل migrate في منتصف الطريق.
- عدم تطابق ModelSnapshot مع النموذج بعد الإصلاحات الطارئة.
- أثر مالي غير متسق بين Order.SellAmount والمدفوعات والتقارير.

## هـ) تحقق بعد الرجوع

- عدد migrations = المتوقع للإصدار الهدف.
- Login + صلاحيات OutsideAll/قوالب أدوار لم تُضاعف بالـseed.
- لا ManagePermissions بالخطأ على حسابات BM.
