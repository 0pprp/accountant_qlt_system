# 03 الرسائل والشكاوى

أنت تنفّذ داخل C:\GitHub\accountant_qlt_system. المرجع القديم للقراءة فقط C:\GitHub\SalesHaider-main\SalesHaider-main. اقرأ AGENTS.md وحالة git قبل أي تعديل؛ لا تستبدل تغييرات موجودة ولا تربط التشغيل بالـAPI القديم.
المستخدم يريد لوحة ويب واحدة بصلاحيات على التبويب والإجراء، والتطبيقات الثلاثة تعمل على API المركزي نفسه. وافق على اعتماد الترقيات الرسمية مع مراجعتها وتجربتها على نسخة معزولة ونسخة احتياطية قبل التفعيل. لا تعتبر ذلك إذنًا لحذف بيانات أو استيراد بيانات النظام القديم.
حافظ على Clean Architecture: Domain للحالات والقواعد، Application لـCQRS والتحقق والنطاق، Infrastructure لـEF والتخزين، Api لعقود HTTP فقط. في Vue افصل domain/types وqueries/mutations وcomposables وcomponents/views؛ استخدم axios والجلسة وQuery cache الحالية.
الأمان: branchId من نطاق الحساب في DB؛ تحقق المورد نفسه والموظف المستهدف في كل قراءة وكتابة وتنزيل. اسم الدور ليس بديلًا لصلاحية الإجراء، والاستثناء الوحيد حماية Admin الحالية. لا تمنح صلاحيات الإدارة الجديدة إلى Permissions.All، ولا توسع دورًا افتراضيًا بلا سياسة معلنة. الهوية والوقت من السيرفر. لا تعرض المال المخفي كصفر. لا بيانات وهمية عند فشل API.
التصميم: RTL، ElMessiri، #006A64 و#00201E و#F8F8F8؛ استخدم Select/MultiSelect المشتركة choice.css ونوافذ PrimeVue الوسطية. خط النص 16px والعناوين 20–24px وأهداف اللمس 44px. لا تخف معلومات العمل بالتقصير؛ أظهر الأقسام والأسباب والمرفقات وسجل الحركة. التصميم يعمل على 360/768/1440.
كل تعديل حالة يحتاج expectedVersion و409 عند التعارض وسبب إذا تطلب العمل ذلك، ومعاملة ذرية وتدقيق before/after دون أسرار. امنع النقر المكرر وإعادة المحاولة من تكرار الأثر. تحديثات realtime تحمل IDs/revision فقط وبمجموعات محسوبة من السيرفر؛ أعد استعمال نمط outbox مع تصميم كيان مناسب للمجال.
حدّث docs/management-rollout: Excel للـendpoints والعقود والصلاحيات والفروع والحالة، Word لمسارات الملفات ومسؤوليتها، ودليل قبول يفرق Source-reviewed / Implemented / Unit-tested / Live-verified / Blocked. لا تعلن اكتمال ما لم تختبره. اختبارات 401/403، فروع A/B، IDOR، تعارض متزامن، تحديث الجلسة/الصلاحيات، وإعادة المحاولة مطلوبة عندما ينطبق ذلك. لا تولّد tests شكلية. لا تُفعّل إنتاجًا مع فشل البناء أو schema غير متطابق.

## تنفيذ هذه المرحلة

اقرأ delegated_manager_application/lib/features/complaints وdocs/delegated-manager-api.md؛ استخرج حقول الرسالة وحالة القراءة والمرسل والمصدر. أنشئ ComplaintAggregate ومجلد Application/Complaints وعقود GET admin/Complaints، GET {id}، PUT {id}/read، PUT read-all، وPOST app/Complaints.
صلاحيات Complaint.Read/MarkRead/Submit، الفروع من الحساب، والمرسل والمصدر المسموح من الجلسة. حد الرسالة 10–2000 من المرجع؛ راجع بقية الحدود من handler القديم. اجعل read-all محددًا بفروع وفلاتر العرض، لا كل المؤسسة. لا تضف Reply/Close إن لم تثبت دورة العمل في المصدر.
أضف تبويب المفوض صندوق الرسائل: إجمالي غير المقروء المسموح، صفوف تحمل عنوانًا ومرسلًا ومصدرًا ومحافظة ووقتًا، تفاصيل نص كامل. صحّح العدادات بعد read وعند reconnect. نموذج الشكوى في التطبيقات يستخدم نفس العقد ولا يرسل gateway key أو بيانات هوية موثوقة من العميل. اختبر المصدر المزور، branch خارج النطاق، pagination، وإعادة mark-read دون أثر مكرر.
