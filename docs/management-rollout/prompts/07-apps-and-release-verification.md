أنت تنفّذ داخل C:\GitHub\accountant_qlt_system. المرجع القديم للقراءة فقط C:\GitHub\SalesHaider-main\SalesHaider-main. اقرأ AGENTS.md وحالة git قبل أي تعديل؛ لا تستبدل تغييرات موجودة ولا تربط التشغيل بالـAPI القديم.
المستخدم يريد لوحة ويب واحدة بصلاحيات على التبويب والإجراء، والتطبيقات الثلاثة تعمل على API المركزي نفسه. وافق على اعتماد الترقيات الرسمية مع مراجعتها وتجربتها على نسخة معزولة ونسخة احتياطية قبل التفعيل. لا تعتبر ذلك إذنًا لحذف بيانات أو استيراد بيانات النظام القديم.

## تنفيذ هذه المرحلة

راجع التطبيقات الجديدة sales_employee_app وdelegate_app وcommittee_officer_application؛ لا تنسخ branch_manager_application القديم بكامل إعدادات الشبكة. إدارة الفرع والمفوض انتقلت للويب، إلا إذا طلب المستخدم APK مستقلًا لهما. شغّل flutter doctor/devices وحدد target الممكن فعليًا؛ لا تعتبر web إثبات Android.
ثبّت API_BASE_URL أو API_BASE وفق config كل تطبيق للدومين الجديد، tokens/session/branch scope، لا تخزن أسرار السيرفر في Dart. اختبر login/refresh/logout، طلب مبيع من كل تطبيق ثم ظهوره غير مسند، الإسناد A→B ومنع A، تجهيز/كشف/بيع، الشكاوى/المهام حسب العقود المنفذة. لا GPS stub في build إنتاج ولا بيانات demo عند API failure.
لا ترفع batch جميع المراحل مرة واحدة. لكل إصدار: build/tests، migration review، has-pending-model-changes، clone production بالوصول المقيد، backup حديث، فحص read/write على clone، صور rollback، تفعيل، فحص عام ثم cleanup. لا تنزل توكنات أو dumps إلى الحاسوب بلا إذن صريح؛ استخدم جلسة المستخدم المصرح بها في المتصفح دون تصدير أسرار.
حدّث Excel/Word والقبول عند كل دفعة. لا تغيّر كل شيء في وقت واحد لإرضاء سقف أربع ساعات؛ نفّذ المسار المثبت أولًا، واذكر المتبقي بالاسم. إصدار APK يحتاج build release والتوقيع المناسب وملف hash وطريقة تثبيت؛ لا تطلب تثبيت VS كامل إذا Android target متاح. احتفظ بتغييرات الزملاء وراجع git diff قبل النشر.
