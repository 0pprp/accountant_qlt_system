# برومبت تنفيذي 01 — لوحة متابعة المندوبين

**الحالة:** جاهز للمراجعة — **لا تنفّذ قبل اعتماد المقارنة.**  
**الأولوية:** 1 من 3 (ثم عمل المتابعين، ثم الملخص).  
**نوع العمل:** تطابق وظيفي مع المرجع؛ تحسين شكل/أداء مسموح؛ لا تغيير قواعد العمل.

---

## 1) الاسم والمكان والأدوار

| | |
|---|---|
| الاسم الظاهر | **متابعة المندوبين** |
| المكان الصحيح في التنقل | مستوى المدير/المراقب (أو صلاحية مكافئة في اللوحة الموحدة) — **ليس** تحت «إدارة الفرع › متابعة المبيعات» ولا تحت «المدير المفوض › تقييم موظفي المبيعات» |
| الأدوار المستفيدة | المدير + المراقب (كما في `FE_Company` router: `directorAllowed` + `monitorAllowed`) |
| المسار المقترح في الجديد (عند التنفيذ) | مثلاً `/management/director/delegate-followup` — يُثبَّت عند التنفيذ دون كسر مسارات SalesFollowup الحالية |
| ما يجب عدم لمسه | الإبقاء على `SalesFollowup` كمتابعة **موظفي المبيعات**؛ فك أي تسمية توحي أنها متابعة مندوبين |

## 2) ملفات المرجع وقواعد العمل المطلوب نقلها

### واجهة

- `FE_Company/src/pages/director-delegate-followup.vue` — اللوحة الكاملة
- `FE_Company/src/pages/director-delegate-followup-customers.vue` — صفحة التفاصيل (برومبت فرعي لاحق P-DF-04)
- `FE_Company/src/composables/directorApi.js` — دوال `directorDelegateFollowup*`
- `FE_Company/src/navigation/vertical/index.js` — مدخل القائمة
- `FE_Company/src/plugins/1.router/index.js` — حراسة المدير/المراقب

### خلفية

- بوابة: `BE_SalesEmployee/Controllers/DirectorController.cs` — مسارات `delegate-followup/*`
- شركة: `BE_Company/Sales/Controllers/DirectorDelegateFollowupController.cs`
- خدمة: `BE_Company/Sales/Services/DirectorDelegateFollowupService.cs`  
  (`GetActiveListsAsync`, `GetListSummaryAsync`, `GetListCustomersAsync`, BoardOperator rating)
- قواعد: `DirectorDelegateFollowupRules.cs` (`MaxDaysListActivity = 40`, نطاقات الباقي، القسط المطلوب)
- تقييم الزبون: `CustomerRatingCalculator` / `CustomerRatingModels.cs`

### قواعد عمل ملزمة (من المصدر — لا تخمين)

1. وحدة العمل = **قائمة مندوب** (`listId` = DelegateID)، وليست موظف مبيعات.
2. القائمة «نشطة» إن `DelegateState` فعّال وآخر تسديد ضمن **40 يوماً** (`MaxDaysListActivity`).
3. التنقل: محافظة → بطاقات قوائم → لوحة مؤشرات → جدول زبائن (أو صفحة تفاصيل).
4. جدول الزبائن مخفي افتراضياً؛ يظهر عند اختيار فئة/نطاق باقي/قانونية أو «عرض التفاصيل».
5. فلاتر الجدول على الواجهة: `all` | فئات التقييم | `legal` | `lt100` | `100to200`.
6. تقييم عامل اللوحة: درجة صحيحة 0–10، ملاحظة اختيارية، **تقييم واحد لكل قائمة في اليوم** (MERGE)، يُحفظ عبر POST.
7. بروفايل الزبون مع `returnTo` يعيد للوحة بنفس `city` + `listId`.
8. لا تستبدل هذه اللوحة بتقييم موظفي المبيعات ولا بمهام إدارية.

**غير محسوم — يُستخرج قبل التنفيذ ولا يُخترع:**  
قصد دخول القانونية في عدّادات الفئات مقابل استثنائها من فلتر الجدول؛ هدف التحويل «قانونية» دائماً 0؛ محاكاة weekAgo على زبائن اليوم.

## 3) البيانات وترتيب العرض (اللوحة الرئيسية — نطاق هذا البرومبت)

### أ) منتقي المحافظة

بطاقات: اسم المحافظة + قيمة المدينة.

### ب) بطاقة قائمة

- اسم القائمة
- التقييم الحقيقي (رقم + تسمية)
- عدد غير المصفرين
- تاريخ آخر تسديد

### ج) رأس التفاصيل

اسم القائمة؛ أزرار: تغيير المحافظة، رجوع للقوائم، عرض التفاصيل.

### د) قسم التقييمات (كروت)

التقييم الحقيقي (+ اتجاه أسبوع) · تقييم عامل اللوحة (+ زر تقييم اليوم) · تقييم مسؤول اللجنة · تقييم لجنة الإشراف · تقييم مندوب المبيعات — مع نوافذ تاريخ 30 يوماً.

### هـ) قسم الواردات

القسط المطلوب اليوم · مبيعات جديدة بدون جباية (3أيام+) · وارد أمس · وارد آخر جمعة · واردات الفئات الخمس.

### و) قسم غير المصفرين

كروت الفئات + باقي &lt;100ألف + 100–200ألف + القانونية — تضغط لإظهار/إخفاء الجدول بفلتر.

### ز) قسم التحويل

نص الملخص + كروت «إلى {فئة}» مع تفاصيل المتحولين.

### ح) جدول الزبائن (عند الظهور)

الأعمدة الافتراضية بالترتيب المرجعي: بروفايل، العميل، التقييم، تاريخ البيع، سعر البيع، الواصل، الباقي، القسط، آخر تسديد، مبلغه، نسبة التسديد، عدد التسديدات، عدد الأيام، العنوان، الهاتف، اسم المحل، الجابي، البائع، المباعة، الملاحظات.  
إجراءات: ترتيب أعمدة، تصدير، صفحة التفاصيل الكاملة، إخفاء.

*(تفاصيل صفحة الزبائن الكاملة / التسديدات / مجموع الفترة = برومبتات فرعية لاحقة — لا توسّع هذا البرومبت لتنفيذها الآن.)*

## 4) عقود API الموجودة لإعادة الاستخدام

من المرجع (أسماء الشركة؛ تُكيَّف لاحقاً لمسارات Admin الجديدة **بعد التحقق** من عدم وجود مقابل في النظام الحالي):

| Method | Path (شركة) | استخدام |
|---|---|---|
| GET | `.../director-delegate-followup/lists` | بطاقات القوائم |
| GET | `.../lists/{listId}/summary` | لوحة المؤشرات |
| GET | `.../lists/{listId}/customers` | صفوف الجدول |
| GET/POST | `.../lists/{listId}/board-operator-rating` | قراءة/حفظ تقييم عامل اللوحة |

حقول الاستجابة الجوهرية موثّقة في تدقيق المصدر (listId, listName, realRating*, nonZeroed*, tier*, remaining*, conversion, boardOperatorRating, …).

**في النظام الجديد حالياً:** لا يوجد مقابل لهذه العقود تحت `/admin`.  
`/admin/SalesFollowup/*` **ليس** بديلاً مناسباً (SellerId ≠ DelegateID).

## 5) عقود ناقصة مقترحة (منفصلة بوضوح — لا تُنفَّذ قبل التحقق)

- تكييف عقود lists/summary/customers/board-operator-rating إلى نطاق Clean Architecture + صلاحيات + branch/city scope في النظام الجديد.
- أي جدول تخزين لتقييم عامل اللوحة إن لم يوجد مكافئ — **بعد** البحث في الـDB الجديدة؛ لا إنشاء جدول قبل التحقق.
- مدن/محافظات: التحقق أولاً من `Branches`/`Provinces` الحالية كبديل لـ `director/cities`.

لا تقترح CreatePayment أو list-payments-sum داخل هذا البرومبت (P-DF-02 / P-DF-06 لاحقاً).

## 6) الصلاحيات والنطاق

| عملية | من يستعمل | نطاق |
|---|---|---|
| قراءة قوائم/ملخص/زبائن | المدير + المراقب (أو صلاحيات Read مكافئة منفصلة عن SalesFollowup) | محافظة/مدينة مختارة؛ قائمة ضمن نطاقه |
| حفظ تقييم عامل اللوحة | نفس الأدوار المسموح لها في المرجع | listId + يوم العراق؛ لا يقبل displayName من العميل كمصدر ثقة |
| فتح بروفايل زبون | صلاحية بروفايل موجودة إن توفرت | نفس المدينة/الفرع |

**لا تُمنح لـ Permissions.All.** لا توسّع دوراً افتراضياً بلا سياسة معلنة.

## 8) سيناريوهات قبول (نفس المدخلات → نفس النتائج المرجعية)

1. مستخدم مدير يختار محافظة فيها قوائم نشطة → يرى بطاقات بنفس ترتيب المرجع (آخر تسديد ثم الاسم).
2. قائمة بلا تسديد &gt;40 يوماً → **لا** تظهر ضمن النشطة.
3. فتح قائمة → تظهر أقسام التقييمات/الواردات/غير المصفرين/التحويل؛ الجدول مخفي.
4. ضغط «ممتاز» → يظهر الجدول مفلتراً على ممتاز غير قانوني؛ الضغط ثانية يخفي.
5. حفظ تقييم عامل اللوحة 8 مع ملاحظة → يظهر على الكرت لليوم؛ إعادة الحفظ تستبدل نفس اليوم.
6. درجة 11 أو −1 → رفض.
7. حساب بلا صلاحية → 401/403؛ لا بيانات وهمية.
8. مقارنة عيّنة listId مع استجابة المرجع (lists+summary+customers) لنفس المدينة — الحقول الظاهرة متطابقة ضمن هامش غير المحسوم الموثّق.
9. SalesFollowup الحالية تبقى تعمل لموظفي المبيعات دون انكسار بعد إضافة اللوحة الجديدة.
